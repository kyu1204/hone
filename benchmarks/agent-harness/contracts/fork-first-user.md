- Background: `docs/correction.md` (Fork) and `docs/work-orders/T-701.md` describe forking. They describe the re-run from the edited prefix and do not cover the two rules below, which are required.
- The change is in `forkTrial(req)` (`src/correct/fork.ts`). `ForkRequest` keeps its fields.
- Input for the re-run: when `req.step` is the index of the first `role: "user"` message of the original trace, and `req.edited` is a user message whose `content` is a string, that content is the input. In every other case the input is `req.caseInput`, as today.
  - This input is what the target receives (`target.resume(prefix, input, ctx)` when the target has `resume`, otherwise `target.run(input, ctx)`), and it is also the `case.input` the scorers see.
- Final turn: after the prefix handling that exists today, when the forked trace has no error and holds exactly as many messages as the prefix (the target recorded nothing beyond the prefix), one message is appended: `{ role: "assistant", content: <answer> }`, where `<answer>` is `trace.output` when it is a string and its JSON text otherwise. Nothing else is added to that message. `trace.meta.synthesizedMessages` is then set to `true`, the marker the executor's `ensureMessages` in `src/targets/target.ts` already uses.
  - So forking a plain `fn` target at its first user message gives a trace whose messages are exactly the edited user message followed by the assistant message carrying the new output.
- A trace that already has messages beyond the prefix, or that has an error, gets no extra message.
- Unchanged: the prefix is `messages.slice(0, step)` plus the edited message; `ctx.prefix`; `trace.meta.forkStep` and `trace.meta.forkedFrom`; the `forked-from:<id>` flag; the next free trial index; the pass rule; storing the trial; `loadForkDeps`.
