# T-903 Release workflow: trusted publishing, compiled binaries, GitHub Release

## Goal
Pushing a `v*` tag publishes `hone-eval` to npm with provenance and attaches six compiled binaries to a GitHub Release, with no long-lived secrets.

## Design
- `scripts/build-binaries.ts`: `bun build --compile src/cli.ts` for `bun-linux-x64`, `bun-linux-x64-musl`, `bun-linux-arm64`, `bun-darwin-x64`, `bun-darwin-arm64`, `bun-windows-x64`, into `dist/bin/hone-<version>-<platform>[.exe]`, then `dist/bin/SHA256SUMS`. `--only <platform>` for local use. Also `bun run build` keeps producing `dist/cli.js` for the npm package.
- `.github/workflows/release.yml`: `on: push: tags: ["v*"]`; `permissions: contents: write, id-token: write`; jobs: `check` (bun run check), `binaries` (matrix over the six targets on ubuntu, cross-compiling with `--target`), `publish` (needs both; `bun publish --provenance --access public` using npm trusted publishing (OIDC), no `NPM_TOKEN`; fails loudly if the tag does not equal `package.json` version), `release` (`gh release create` with the binaries, SHA256SUMS and auto-generated notes).
- `scripts/release-check.ts`: verifies tag == version, `CHANGELOG.md` has a section for the version, the working tree is clean; the workflow and `bun run release:check` both run it.
- `docs/release.md`: the exact steps (bump version, update CHANGELOG, tag, push) and the one-time npm trusted-publishing setup the maintainer must do in the npm UI (hone cannot do it).
- Dry run: `act` is not required; the test `scripts/release-check.test.ts` covers the checks, and `bun scripts/build-binaries.ts --only bun-darwin-arm64` is run locally once to prove the compile works.
