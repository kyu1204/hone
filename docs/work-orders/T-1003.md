# T-1003 `hone sharpen`: the whole cycle, no decisions left to a person

## Goal
One command that evaluates, finds why cases fail, proposes changes, re-tests them, judges each proposal, and confirms the winner on cases it never learned from. In the two studies of 2026-10 a person chained these steps and made the calls (which candidates to combine, how many trials to confirm with); see `docs/benchmarks/`.

## Design
`src/correct/sharpen.ts` exports `sharpen(opts): Promise<SharpenResult>`; `src/cli/commands/sharpen.ts` is the command.

Options: `config, hash, cwd, chat?, budget = 6, holdout = 1/3, trials?, maxCost?, until?, alpha = 0.05, seed = 1, useCache = true, log?`.

1. **Split.** Cases are ordered by a hash of `seed:id`; the first `ceil(n * holdout)` are held out. With fewer than 12 cases, or fewer than 4 held out, nothing is held out and the result says so (`split.inSample = true`). The split depends only on ids and seed, so it is stable between runs.
2. **Measure.** The unchanged config on the dev cases.
3. **Gates.** Stop before spending on proposals when the instrument cannot support them:
   - more than 20% of baseline trials errored: verdict `cannot measure`, with the first error;
   - no dev case fails: verdict `nothing to sharpen`;
   - no `sharpen.variants` and no (`sharpen.text` with a `chat`): verdict `nothing to change`, with the diagnosis and one line on how to declare what may change.
4. **Diagnose.** `clusterFailures` over the failed baseline trials with the offline embedder; with a `chat`, `induceTaxonomy` names the clusters. Each entry: code, definition, size, one example case id.
5. **Propose and verify,** at most `budget` candidates, stopping on `maxCost` or when the best dev rate reaches `until`:
   - first every declared variant, run on all dev cases;
   - then text rewrites. The parent is the best member so far (dev pass rate, then lower cost). One `chat` call gets the parent's text and up to six failure summaries taken round-robin across the parent's failure clusters, so one loud failure mode does not crowd out the others. The child keeps the parent's variant and takes the new text, which is how a rewrite and a variant combine without anyone deciding to combine them. A child runs first on the parent's failing cases plus 8 passing ones and is dropped if it does worse there; otherwise on all dev cases.
   - every candidate goes into the ledger with: kind, label, parent, rationale, the sample result, the dev result, the difference to the baseline, cost, and why it was dropped if it was.
6. **Confirm.** The baseline and the best candidate run on the held-out cases, which no proposal has seen. Paired by case (`compareTargets`):
   - `proven`: the difference is positive and p < alpha;
   - `promising`: positive, not significant. The message gives the interval and how many held-out cases would be needed (`pairsNeeded`);
   - `no gain`: zero or negative. The baseline stays.
   When nothing was held out the same comparison runs on the dev cases and the verdict is at most `promising`.
7. **Report.** `SharpenResult { id, split, baseline, diagnosis, candidates, best?, verdict, message, stopped, path }`, written to `.hone/sharpen/<id>.json`; a winning text also to `.hone/sharpen/<id>-best.txt`. `message` is the plain account the command prints:
   ```
   Now: 71% of 30 cases pass. 14 more cases are held out for the final check.
   Why it fails:
     1. answers-lowercase (9 of 12 failed trials): outputs were not capitalised, e.g. c3
   Tried 3 changes:
     + rewrite 2            71% -> 93%   tell the model to answer in uppercase
     - variant top_k 30     71% -> 70%
     - rewrite 1            dropped early: 40% against 55% on a sample
   Result: PROVEN. On 14 cases it never saw, rewrite 2 takes the pass rate from 69% to 92%
   (+23 points, 95% interval +5 to +41, p = 0.02). Cost per case: 1.1x.
   The new text is in .hone/sharpen/<id>-best.txt
   ```
   Plain statement first, statistics in the parentheses.

Command: `hone sharpen [--budget 6] [--max-cost usd] [--until 0.9] [--trials n] [--holdout 0.33] [--seed n] [--no-cache] [--quiet] [--json]`. Without an LLM key it still runs variants and prints unnamed failure groups. Exit 0 with any verdict except `cannot measure` (exit 1); 2 for usage and config errors. `src/cli.ts` lists `sharpen` as the third everyday command.

## TDD steps
All with `fn` targets and a stubbed `chat`, 30 or more cases so the split is real.
1. Split: stable for a seed, different for another, in-sample below 12 cases.
2. A rewrite that fixes the failures: on the dev side the candidate wins; the held-out comparison is `proven`; the ledger, the file and the best text exist; no held-out case id appears in any prompt sent to `chat`.
3. A variant and a rewrite that each fix half of the failures: the winner carries both.
4. A rewrite that only helps the dev cases (the target passes a case only when its id is named in the text): dev improves, held-out does not, verdict `no gain`.
5. Gates: an erroring target gives `cannot measure`; a passing suite gives `nothing to sharpen`; a config without `sharpen` gives `nothing to change` with a diagnosis.
6. Budget, `maxCost` and `until` each stop the loop.
7. The command: the printed account for cases 2 and 4, `--json`, exit codes.
