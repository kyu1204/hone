# T-1008 Change files: the grammar of an improvement proposal

## Goal
`hone sharpen` runs on proposals that are files. A person writes one, or a coding agent does; the cycle does not care which. This is the place e2e gives its test files (`tests/**/*.e2e.ts`, `test()`, `expect()`): the file is the interface, and skills and MCP only help something write it. Today the proposals are scattered: inline `sharpen.variants` in the config, and model rewrites that exist only in the ledger.

## Design
- `change(name, spec)` exported from the package (`src/correct/change.ts`), called at the top level of a file under `sharpen/`:
  ```ts
  // sharpen/terse-answers.ts
  import { change } from "hone-eval";

  change("answer with the bare value", {
    why: "the cases expect the answer alone; the bot wraps it in a sentence",
    text: "Reply with only the answer.",
  });
  ```
  - `why` (required): the hypothesis. It goes into the ledger and the account.
  - `text`: a new version of the text declared in `config.sharpen.text`.
  - `config`: `(config) => HoneConfig`, any change a config can express: a setting, a model, another function or module for a target. New code lives in a new file or in the change file itself and the config points at it; a change never edits a file the baseline runs, or there is nothing left to compare against.
  - At least one of `text` and `config`; both together are one change.
- `loadChanges(cwd, globs)` imports every file matched by `config.sharpen.changes` (default `sharpen/**/*.{ts,js,mjs}`, test files excluded), in path order, and returns the registered changes with the file each came from. The registry lives on `globalThis` because the published CLI is a bundle and a user's file imports the unbundled package: two module instances. Errors name the file: a throw at import, a missing `why`, neither `text` nor `config`, a duplicate name, a `text` change while the config declares no `sharpen.text`.
- `sharpen()` takes `changes` and searches over three kinds of primitive: config changes (inline variants and changes with `config`), texts (changes with `text`, and model rewrites), and changes that carry both.
  1. every change from a file alone, then every inline variant alone;
  2. then, while the budget lasts: on the best member so far, each untried primitive of the kind it lacks (a config change on a text, a text from a file on a config change); when none is left and there is a model, a rewrite from the best member.
  A text is checked on a sample before its full run, as rewrites are.
- Ledger entries gain `source` (`file`, `config`, `model`), `file` and `why`. Ids: the change's name; `variant <name>`; `rewrite <n>`; `<config change> on <text>` for a pairing.
- A winning text is also written as a change file, `.hone/sharpen/<id>-best.ts`, so a model's rewrite has the same form as a person's and can be moved into `sharpen/` to keep it.
- `Nothing to change` now means: no change file, no variant, and no model for rewrites. Its message shows a three-line change file to start from.
- `examples/sharpen`: the matching setting moves from the config into `sharpen/loose-matching.ts`.
